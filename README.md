# Wallets service — NestJS 12

Сервис на NestJS 12.5 для работы с Ethereum. Требования: Node.js 24.15+ и MySQL 8+ / MariaDB 10.11+.

Сервис хранит адреса, индексирует входящие ETH/ERC-20, обрабатывает реорганизации и отправляет EIP-1559 выводы.
Приватные ключи хранятся в отдельном Go wallet-service. Суммы передаются строками, вычисления выполняются через
`bigint`, в БД — `VARCHAR(78)`.

## Установка и запуск

```sh
npm ci
cp .env.example .env
# Заполнить DB_*, WALLET_SERVICE_*, GATES_API_KEY при необходимости
npm run build
# Только для НОВОЙ пустой базы:
npm run db:migrate
npm run db:seed
npm start
```

API слушает `127.0.0.1:8080`, проверка процесса — `GET /up`. Эта проверка не проверяет соединение с БД или RPC.
`HOST=0.0.0.0` включает внешнее прослушивание. `npm run start:dev` отслеживает изменения и перекомпилирует TypeScript; в
другом терминале `node --watch dist/src/main.js` перезапускает API.

Нужны доступная MySQL/MariaDB, Ethereum RPC и Go wallet-service с маршрутами `POST /api/v1/createaddress`,
`/api/v1/validateaddress`, `/api/v1/tx`. Параметры подключения и авторизации задаются в `.env`.

## База данных

Сервис использует шесть таблиц:

| Таблица          | Назначение                                            |
| ---------------- | ----------------------------------------------------- |
| `gates`          | Сети и активы, параметры RPC и подтверждений          |
| `addresses`      | Адреса и пути деривации                               |
| `blocks`         | Окно проверенных блоков для обнаружения реорганизаций |
| `indexer_states` | Курсор индексатора каждой сети                        |
| `deposits`       | Входящие переводы и их подтверждения                  |
| `withdrawals`    | Выводы, параметры транзакций и состояние отправки     |

Для подключения к подготовленной базе укажите параметры `DB_*` в `.env` и выполните
`npm run cli -- db:verify`. Команда проверяет наличие требуемых столбцов и уникальных индексов, не изменяя данные.
Это не полная проверка типов или содержимого БД. При запуске индексатор продолжает работу с курсора в `indexer_states`.

`db:migrate` предназначена только для пустой БД и откажется работать при наличии любой из шести таблиц. MySQL DDL не
атомарен: при сбое создания схемы проверьте частично созданные таблицы перед повторным запуском. `db:seed` идемпотентно
обновляет настройки двух Sepolia gate; не запускайте её на рабочей БД, если хотите сохранить изменённые вручную
настройки.

## API

При заданном `GATES_API_KEY` все `/api/*` требуют `X-Api-Key`.

| Метод и маршрут            | Поведение                                                                                                        |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `GET /api/addresses`       | До 100 адресов по возрастанию ID                                                                                 |
| `POST /api/addresses`      | `base_gate` (по умолчанию `eth_sepolia`), `account`, `change`, `address_index`; без индекса выделяется следующий |
| `GET /api/deposits`        | Фильтры `status`, `asset_gate`, `address` или `to_address`; до 100, новые блоки первыми                          |
| `GET /api/withdrawals`     | Фильтры `status`, `asset_gate`; до 100, новые ID первыми                                                         |
| `GET /api/withdrawals/:id` | Один вывод                                                                                                       |
| `POST /api/withdrawals`    | `asset_gate`, `to_address`, строковая `amount`; обязательный UUID в заголовке `Idempotency-Key`                  |

Обёртки ответов: `addresses`, `address`, `deposits`, `withdrawals`, `withdrawal`. Подписанные байты не выдаются API.
Числовая `amount`, экспонента, ноль, лишняя точность и переполнение uint256 отклоняются.

```sh
curl http://127.0.0.1:8080/api/addresses -H 'X-Api-Key: YOUR_KEY'
curl -X POST http://127.0.0.1:8080/api/addresses \
  -H 'Content-Type: application/json' -H 'X-Api-Key: YOUR_KEY' \
  -d '{"base_gate":"eth_sepolia","account":0,"change":0}'
```

Создание адреса возвращает 201, существующий путь — 200. Вывод: 201 при новой отправке, 200 при повторном
запросе/подтверждении, 202 для CREATED/SIGNED, 422 для FAILED или ошибки валидации, 409 при повторном ключе с другими
параметрами. Эквивалентные суммы (`1`, `1.00`) считаются одинаковыми. Непредвиденные ошибки сервиса возвращают 500 без
внутренних деталей.

## Команды и индексатор

```sh
npm run cli -- address:create --hot
npm run cli -- address:create --base_gate=eth_sepolia --account=0 --change=0
npm run cli -- address:create --index=15
npm run cli -- blockchain:index --base_gate=eth_sepolia
npm run cli -- blockchain:index --base_gate=ethereum_sepolia --max_blocks=500 --loop --sleep=12
npm run cli -- blockchain:rebroadcast 123
```

`ethereum_sepolia` — синоним `eth_sepolia`. Для запуска раз в минуту используйте cron с абсолютным путём к Node и
`dist/src/cli.js`, предварительно перейдя в папку проекта для загрузки `.env`. Альтернатива — `--loop` под
systemd/supervisor или профиль Docker `indexer`. SIGINT/SIGTERM завершают текущий проход, затем закрывают соединения.

Алгоритм: якорь `start−1` → пакетная загрузка блоков → проверка `parentHash` → успешные native receipts и ERC20 Transfer
logs → атомарная запись блоков/депозитов/курсора → подтверждения и отслеживание выводов → очистка окна. Подтверждения
считаются от проверенной вершины, не от высоты RPC. Native internal transfers из contract traces не индексируются.

Реорганизация ищет общего предка, помечает депозиты `ORPHANED`, возвращает затронутые выводы в `BROADCASTED`, удаляет
блоки выше предка и сканирует заново. Повторно включённый депозит обновляет исходную строку. Потеря уже подтверждённого
депозита выводится в журнал как ошибка. Реорг глубже окна останавливает проход и требует ручного разбора;
автоматического изменения балансов внешней системы нет.

## Надёжность выводов

- Выделение индекса адреса сериализовано блокировкой строки BASE gate (`FOR UPDATE`).
- MySQL `GET_LOCK` сериализует ключ идемпотентности, nonce общего горячего кошелька и индексатор сети между процессами.
  Для ожидания блокировок используется отдельный пул, чтобы не исчерпать пул SQL-запросов. Блокировки привязаны к
  соединению, без истекающего TTL. Все экземпляры должны работать с одним MySQL primary, без маршрутизации блокировок по
  разным серверам.
- SIGNED сохраняется до broadcast. Неопределённый результат остаётся SIGNED; повторная отправка использует те же байты.
  Сохранённые nonce SIGNED/BROADCASTED/CONFIRMED учитываются вместе с `pending` nonce RPC.
- `already known` считается успехом; `nonce too low` сохраняет неопределённый результат, поскольку предыдущая отправка
  могла уже попасть в блок. Остальные явные ошибки ноды дают FAILED.
- CREATED после аварийного завершения процесса автоматически не подписывается заново. Не создавайте новый ключ без
  выяснения состояния исходного вывода. Сервис не реализует ускорение или замену транзакций; разрывы nonce и зависшие
  выводы требуют операционного разбора.

## Особенности работы

- Поле `path` в ответе API адресов содержит BIP44-путь деривации.
- Фильтр депозитов по получателю принимает `to_address` и `address`.
- Пропавшая или отстающая вершина RPC не используется для подтверждения; отсутствующий receipt status не считается успехом.
- Receipts вне сохранённого окна блоков дополнительно сверяются с каноническим блоком RPC.
- Несовпадение хэша в ответе broadcast сохраняет вывод в SIGNED для проверки.
- Индексатор запускается отдельной CLI-командой. Для блокировок используется MySQL; Cache/Redis не требуются.

## Docker

Заполните `.env`, включая непустые `DB_PASSWORD` и дополнительную переменную `MYSQL_ROOT_PASSWORD`. Если локальный порт
3306 занят, измените проброс в Compose.

```sh
docker compose up -d mysql
docker compose build
docker compose run --rm api node dist/src/cli.js db:migrate
docker compose run --rm api node dist/src/cli.js db:seed
docker compose up -d api
docker compose --profile indexer up -d indexer
```

Go-сервис с хоста доступен из контейнера по `host.docker.internal:8000`; другой адрес задаётся через
`DOCKER_WALLET_SERVICE_URL`. Контейнеры не выполняют миграции автоматически.

## Архитектура

Проект разделён на слои Clean Architecture. Домен моделирует адреса, выводы и депозиты
в рамках одного сервиса кошельков; отдельные микросервисы или event sourcing не требуются.

- `src/domain` — предметные типы, неизменяемые `Amount` и `DerivationPath`, агрегат
  `WithdrawalAggregate`, правила депозитов, комиссий и nonce. Здесь нет NestJS, SQL, HTTP
  и чтения переменных окружения.
- `src/application` — сценарии создания адресов, вывода, повторной отправки и индексации,
  а также сервис запросов. `ports` задаёт интерфейсы репозиториев, кошелька, блокчейна,
  блокировок, часов и журнала. Зависимости направлены только на домен и эти интерфейсы.
- `src/infrastructure` — реализации портов: TypeORM/MySQL, RPC, Go-кошелёк, системные часы
  и конфигурация окружения. Репозитории сохраняют существующие таблицы и индексы.
- `src/presentation/http` — контроллеры, авторизация, проверка входных данных, представления
  ответов и преобразование доменных ошибок в прежние HTTP-ответы.
- `src/app.module.ts` — сборка зависимостей: связывает интерфейсы прикладного слоя с адаптерами.
  `src/main.ts` и `src/cli.ts` остаются точками входа HTTP и CLI.

Агрегаты владеют изменяемым состоянием и правилами переходов:

- `WithdrawalAggregate` создаёт вывод только в `CREATED`, проверяет идемпотентность,
  разрешает подпись только из `CREATED`, обрабатывает результат отправки и канонический receipt.
  Сохранённая подпись не становится безопасно отменённой после неоднозначной ошибки;
  запоздавший ответ RPC не понижает `CONFIRMED`. Реорганизация возвращает затронутый вывод
  в `BROADCASTED`, сохраняя подписанные байты.
- `DepositAggregate` распознаёт native/ERC20-поступления, применяет порог подтверждений,
  переводит депозит в `ORPHANED` при реорганизации и восстанавливает его при повторном
  наблюдении с прежним идентификатором.
- `AddressBook` управляет выделением индексов в рамках базового gate; `GateAggregate`
  проверяет допустимость операций и принадлежность активов базовой сети.
- `ChainIndexAggregate` проверяет непрерывность блоков, связь депозитов с блоками и позицию
  индексатора. `ChainReorganization` связывает разрешённый откат с исходной позицией,
  каноническим предком и допустимой глубиной.

У агрегатов выводов и депозитов закрытые поля состояния. Снимки отделены от внутреннего
состояния, включая даты. Создание и восстановление из БД — разные операции:
восстановленный агрегат нельзя повторно вставить как новый. Прямое конструирование
и подмена обычным объектом отклоняются также во время выполнения.

У репозитория выводов нет `update(id, Partial<Withdrawal>)` или сохранения произвольного
снимка. `create(aggregate)` принимает только новый агрегат; `change(id, operation)` загружает
актуальное состояние в транзакции с блокировкой строки, выполняет синхронную доменную
операцию и сохраняет полученное состояние. Возвращённый из callback другой объект
не используется; исключение откатывает транзакцию. Так же обрабатываются подтверждения
депозитов. Репозитории не вычисляют новые статусы SQL-выражениями.

Пакет блоков, депозиты и позиция индексатора сохраняются атомарно. Репозиторий повторно
проверяет переход позиции через агрегат, поэтому произвольный сдвиг курсора невозможен.
Откат загружает все затронутые активы сети, применяет доменные переходы и сохраняет
депозиты, выводы, блоки и позицию одной транзакцией. Ранее массовые SQL-обновления
подтверждений теперь выполняются через отдельные агрегаты; на больших объёмах это требует
больше запросов к БД.

MySQL-блокировки идемпотентности, nonce и индексатора сохраняют прежнюю область действия.
Подписанные байты по-прежнему сохраняются до отправки. Проверка подписанта выполняется
агрегатом на текущем состоянии под блокировкой строки.

`rpc_url` и `wallet_gate` остаются в таблице и инфраструктурных сопоставлениях, но отсутствуют
в доменной модели `Gate`. Адаптеры разрешают эти настройки по идентификатору gate.
Сессия кошелька создаётся до транзакции выделения адреса, чтобы внутри неё не занимать
дополнительное соединение для чтения настроек.

Сопоставления таблиц описаны через `EntitySchema` в
`src/infrastructure/persistence/entities.ts`, поэтому доменные классы не содержат ORM-декораторов.
Репозитории используют TypeORM Repository/QueryBuilder, а транзакции — EntityManager.
Подключения открываются при первом обращении к БД; health endpoint не требует доступной MySQL.
Для именованных блокировок выделен отдельный DataSource с QueryRunner на одном соединении.

`synchronize` и автоматический запуск миграций отключены. `db:migrate` запускает явную начальную
миграцию TypeORM и создаёт служебную таблицу `migrations`. При наличии любой прикладной таблицы
команда завершается до изменения схемы: для существующей Laravel-БД используется `db:verify`.
`db:seed` повторяемо обновляет справочники, сохраняя их идентификаторы. Тесты используют тот же
набор EntitySchema и миграцию с SQLite-драйвером, совместимым с TypeORM.

## Проверки

```sh
npm test
```

Тесты написаны на TypeScript и используют Jest (`@jest/globals`). Команда сначала очищает `dist` и компилирует проект,
затем запускает Jest для `dist/test/**/*.test.js`. Для ESM используется `--experimental-vm-modules`
согласно [документации Jest](https://jestjs.io/docs/ecmascript-modules).
Для запуска отдельного набора: `npm test -- --runTestsByPath dist/test/amount.test.js`.

Тесты проверяют границы архитектуры, доменные правила и запрет их обхода через репозитории,
сценарии через подменяемые порты,
атомарность репозиториев, точность сумм, ERC20 ABI, настоящий HTTP API NestJS и формат ошибок,
клиент RPC с локальным HTTP-сервером,
идемпотентность, параметры EIP1559, таймаут/повторную отправку, подтверждения и реорганизации. Тесты сервисов используют
временную SQLite в памяти и имитацию Go/RPC; блокировки MySQL заменены локальным mutex. Они не заменяют проверку на
MySQL и интеграцию с реальным Go-сервисом/Sepolia. Реальные транзакции при тестировании не отправляются.

Официальная справка: [документация NestJS](https://docs.nestjs.com/).
